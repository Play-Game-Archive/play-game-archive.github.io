5000 Characters at Video Frame Rate using Declarative Programming

以声明式编程让5000个角色按视频帧率运行

Samuel Hill 塞缪尔·希尔 / Ian Horswill 伊恩·霍斯威尔 · 2025 · 2026汉译

简介

论文以州博览会模拟为实例，使用声明式逻辑编程实现基于需求的角色行动选择。作者结合原生C#编译、按谓词并行求值和带时间戳的需求状态，在Apple M3 Pro上运行5000个角色，并报告帧时间及动作选择成本。其结果建立在每个地点提供一种行动、每个行动满足一种需求、粒子式角色渲染和简单直线移动等具体条件之上。正文及代码附录给出了评分、选择、移动接口、计时和需求更新的实现。

Abstract

Video games have historically been limited in the number of characters under AI control. This is all the more true for games that use declarative systems which are generally used for turn-based or otherwise non-real-time games. While a declarative system can obviously be used for a real-time simulation, we wanted to test the limits of how far it can be scaled for large numbers of characters. This paper shows how 5000 characters can run simultaneously and in real-time with 60fps performance on a modern laptop using a declarative logic programming language.

摘要

电子游戏中受人工智能控制的角色数量，历来受到限制。对于使用声明式系统的游戏来说，这一点尤为明显，因为此类系统通常用于回合制游戏或其他非实时游戏。声明式系统显然可以用于实时模拟，但我们希望测试：当角色数量很大时，这种系统的规模究竟能够扩展到什么程度。本文展示了如何使用一种声明式逻辑编程语言，在现代笔记本电脑上让5000个角色同时实时运行，并达到60fps的性能。

1. Introduction 1. 引言

Performance considerations have traditionally restricted the number of simultaneous NPCs, particularly when those characters are driven by symbolic rules or other declarative methods. Many systems that do support this kind of character AI are also turn-based rather than real-time. In this paper, we show that 5000 The Sims-style characters can be run simultaneously on a modern laptop using a version of logic programming.

性能方面的考虑，历来限制了能够同时存在的NPC数量，尤其当这些角色由符号规则或其他声明式方法驱动时。许多确实支持这类角色人工智能的系统，同样采用回合制而非实时运行。本文展示，使用逻辑编程的一种实现，可以在现代笔记本电脑上同时运行5000个《The Sims》式的角色。

Although Sims-style ‘needs-based AI’ is relatively simple, and the rendering of the characters in our demo is extremely simple (particle-like dots on the screen), this still demonstrates that symbolic, declarative techniques can be pushed well beyond what would have been though possible. In this paper, we will discuss the system, and the techniques used to make it so efficient.

尽管《The Sims》式的“基于需求的人工智能”相对简单，我们的演示中角色的渲染也极为简单——只是屏幕上类似粒子的圆点——但这依然说明，符号式、声明式技术能够被推进到远远超出原先可能设想的程度。本文将讨论这一系统，以及使它如此高效的技术。

2. Related Work 2. 相关工作

Many AI-based games have used symbolic declarative systems - logic, symbolic rules, or some kind of rule engine - for social reasoning and character control. Façade [1] used a reactive planner, ABL [2], that incorporated a forward-chaining production system. Prom Week [3] also used a forward-chaining production system, Comme Il Faut [4]. CiF’s successor the Ensemble Engine [5] is similarly a forward-chaining production system. The Sims 3 [6] used a rule system to script the interactions between situations, personality traits, and actions available to a given character [7]. MKULTRA [8] and City of Gangsters [9] both used logic programming to implement social reasoning [10]. F.E.A.R. makes use of a planner, GOAP, that allows for declarative definitions of various AIs in the GDBEdit database tool [11].

许多以人工智能为基础的游戏，都曾使用符号式的声明式系统——逻辑、符号规则或某种规则引擎——来进行社会推理和角色控制。《Façade》[1]使用了反应式规划器ABL[2]，其中包含一个前向链接产生式系统。《Prom Week》[3]同样使用前向链接产生式系统Comme Il Faut[4]。CiF的后继者Ensemble Engine[5]也是一种前向链接产生式系统。《The Sims 3》[6]使用规则系统，编写情境、人格特质和特定角色可用行动之间的相互关系[7]。《MKULTRA》[8]与《City of Gangsters》[9]均使用逻辑编程实现社会推理[10]。《F.E.A.R.》使用GOAP规划器，可以在GDBEdit数据库工具中，以声明式方式定义各种人工智能[11]。

One of the earliest and most influential symbolic systems for games is the Inform 7 language [12], [13] that allows designers to build interactive narrative systems using declarative statements. The Versu simulationist narrative system [14], [15] used a custom logic programming language, Praxis, based on an exotic modal logic called eremic logic (aka exclusion logic) [16]. The Lume system [17] made extensive use of Prolog’s definite clause grammars [18], [19] for text generation. Lapeyrade has also used Prolog for better character decision making [20].

用于游戏的最早、最具影响力的符号系统之一，是Inform 7语言[12], [13]；设计者可以用声明式语句构建交互叙事系统。模拟主义叙事系统Versu[14], [15]使用了一种定制的逻辑编程语言Praxis，它以一种特别的模态逻辑eremic logic（又称排除逻辑）为基础[16]。Lume系统[17]广泛使用Prolog的定子句文法[18], [19]来生成文本。Lapeyrade也曾使用Prolog来改善角色决策[20]。

All these games and systems use declarative programming for either some component of character control and/or social reasoning. Some are turn-based games like in the Versu platform, others are batch like jobs used in Townlikes (that still need to run fast but not at any particular frame rate), and others are real-time systems like with GOAP in F.E.A.R.. Even when used for real-time character control the number of NPCs is usually relatively low and the portion of the game logic that is declarative are the relations between possible actions and the world state. The code for how a Goal executes is still usually written in an imperative manner [11].

所有这些游戏和系统，都在角色控制的某些组成部分和／或社会推理中使用声明式编程。其中一些是Versu平台那样的回合制游戏，一些是Townlikes中使用的批处理式任务（仍然需要快速运行，但无须满足某一特定帧率），还有一些是实时系统，例如《F.E.A.R.》中的GOAP。即便用于实时角色控制，NPC数量通常仍相对较少，而且游戏逻辑中采用声明式表达的部分，是可能采取的行动与世界状态之间的关系。某个目标具体如何执行，其代码通常仍以命令式方式编写[11]。

There are also entire games that have been built using declarative languages, such as those built with the video game description language - VGDL [21]. Currently this technique is used to generate 2D tile arcade style games with the help of ASP and evolutionary search [22], [23]. These games are playable by a human and are fully declarative - everything from character controls to game logic to the tilemap itself are declared in text files that are used to generate a game. The purpose of these games is largely to allow for testing of general video game playing (GVGP) algorithms on several different games [24].

还有一些游戏，整个游戏都是用声明式语言构建的，例如使用电子游戏描述语言VGDL[21]制作的游戏。目前，这种技术在ASP与演化搜索的辅助下，用于生成二维图块式街机游戏[22], [23]。这些游戏可以由人类游玩，而且是完全声明式的：从角色控制、游戏逻辑到图块地图本身，所有内容都在用于生成游戏的文本文件中声明。这些游戏主要是为了能够在若干不同游戏上，测试通用电子游戏游玩（GVGP）算法[24]。

In large part because of the expense of AI simulation, games involving large-scale character simulation are relatively rare. The best known is Dwarf Fortress [25], which supports real-time simulation of small hundreds of characters. Achieving this level of performance requires implementation in C++ and significant programmer effort to optimize cache locality and minimize pointer chasing. RimWorld is a very similar game that also involves social simulation for the purpose of storytelling [26]. Caves Of Qud is a game that is more like adventure mode in DF and, similarly, features hundreds of characters that all have various social relations and need to choose what action to take each tick [27]. Unlike DF Fortress mode and RimWorld, this roguelike experience is turn based and as such doesn’t need to run at a particular frame rate. While all these games feature large numbers of characters acting in a world, none use declarative systems for the control of these NPCs.

涉及大规模角色模拟的游戏相对罕见，很大程度上是因为人工智能模拟的开销高昂。其中最著名的是《Dwarf Fortress》[25]，它支持数百个、但数量不算多的角色的实时模拟。要达到这种性能水平，需要用C++实现，并由程序员投入大量精力，优化缓存局部性、尽量减少指针追踪。《RimWorld》是一款非常相似的游戏，同样为了故事讲述而进行社会模拟[26]。《Caves Of Qud》更接近《Dwarf Fortress》（DF）的冒险模式，同样包含数百个具有各种社会关系的角色，而且每次更新都需要选择行动[27]。与DF的要塞模式和《RimWorld》不同，这种roguelike体验采用回合制，因此无须以某一特定帧率运行。虽然这些游戏都有大量角色在世界中行动，但它们都没有使用声明式系统来控制这些NPC。

Some large-scale crowd simulation exist for use in film and other rendered media forms [28], [29]. Some of these tools even allow the behaviors of the agents to be stated in sentence form for specific decision nodes [30]. These tools target rendered scenes for film and television and as such do not need to run in real-time.

一些大规模群体模拟系统用于电影及其他渲染媒介[28], [29]。其中一些工具甚至允许在特定决策节点上，以句子的形式描述智能体行为[30]。这些工具面向电影和电视的渲染场景，因此无须实时运行。

Some crowd simulation techniques have been used to study crowd dynamics and the creation of autonomous agents for visualization [31], [32]. Shao have claimed real-time performance at 30fps when animating up to 1400 characters moving and pathfinding around a 3D scene on 2007 hardware [31]. This was done with over 50,000 lines of C++ and uses a simple action selection method reminiscent of needs-based AI.

一些群体模拟技术曾用于研究群体动力学，以及为可视化创建自主智能体[31], [32]。Shao曾报告：使用2007年的硬件，为多达1400个在三维场景中移动、寻路的角色制作动画时，可以达到30fps的实时性能[31]。这一实现使用了超过50,000行C++代码，以及一种让人联想到基于需求的人工智能的简单动作选择方法。

3. Needs-based AI 3. 基于需求的人工智能

Needs-based AI is a famous technique for controlling characters in video games that was created for The Sims [33], [34], and has been used in other games like Roller Coaster Kingdom and an RPG for Lord Of the Rings [34].

基于需求的人工智能，是一种著名的电子游戏角色控制技术，最初为《The Sims》创立[33], [34]，也用于《Roller Coaster Kingdom》和一款《Lord Of the Rings》角色扮演游戏等其他游戏[34]。

Needs-based AI attempts to fulfill various needs for NPCs by searching over the actions of each object available to them (i.e. advertisements) and weighting the cost of completing the action against each character’s needs with some scoring function [34]. Each character goes about completing actions that have been selected/assigned to them, potentially getting rewarded for the various tasks. When no more actions remain in the queue of selected actions the NPC searches for all the advertisements on all the objects around them then scores each action based on their needs and selects the best scoring advertisement. The equation for selecting the best scoring advertisement is argmax(S) where S is the set of all scored advertisements for a given character.

基于需求的人工智能尝试满足NPC的各种需求：它搜索NPC可用的各个物体所提供的行动（即“广告”，advertisements），再通过某种评分函数，结合每个角色的需求，对完成行动的成本进行权衡[34]。每个角色会去完成已为自己选择或分配的行动，并可能因完成不同任务而获得奖励。当已选行动的队列中不再有待执行行动时，NPC便搜索周围所有物体上的全部广告，依据自身需求为各个行动评分，并选择得分最高的广告。选择最高分广告的公式为argmax(S)，其中S是某个角色的所有已评分广告所构成的集合。

The complexity of scoring all advertisements is O(NLM), where N is the number of people, L is the objects nearby, and M is the advertisements at each location. Once you have scored all advertisements for all characters, you can run the argmax equation for each character. Since argmax is operating on the set of all advertisements for each person, the complexity of selecting an action from the scored set is O(NLM), where N is the number of people, L is the objects nearby, and M is the advertisements. Given that these two steps are each of the same complexity, and that the two iterations are sequential, the total complexity of action selection is O(NLM).

为全部广告评分的复杂度为O(NLM)，其中N是人数，L是附近的物体数，M是每个地点上的广告数。为全部角色的所有广告评分之后，就可以对每个角色运行argmax公式。由于argmax处理的是每个人的全部广告所构成的集合，从已评分集合中选择一个行动的复杂度也是O(NLM)，其中N是人数，L是附近的物体数，M是广告数。鉴于这两个步骤的复杂度相同，而且两次迭代是顺序执行的，因此动作选择的总复杂度为O(NLM)。

The selected advertised action sequence is then added to the queue of actions to be completed. Needs-based AI has always had the ability to sequence actions, a technique called action chaining [34], but in The Sims 4 the developers wanted to be able to have more interesting action sequences. To accomplish this the developers allowed the system to simultaneously dispatch multiple actions from the queue when those actions would not interfere with one another [35].

接着，被选中的广告行动序列会加入待完成行动的队列。基于需求的人工智能一直具备把行动排成序列的能力，这种技术称为动作链[34]；不过，《The Sims 4》的开发者希望能够拥有更有趣的行动序列。为此，开发者允许系统在多个行动彼此不会干扰时，从队列中同时派发这些行动[35]。

The Sims 3 had a goal of creating a larger varied living world, and to do this while remaining playable several optimizations were employed [36]. Some execution optimizations such as hierarchical planning and commodity-interaction maps as well as some level of detail (LoD) optimizations such as auto-satisfy curves and story progression [36]. Hierarchical planning takes the usually O(NLM) approach of searching for every person (N), for every location (L), and then for every advertised action (M), and makes it O(N + L + M) by instead selecting each step one at a time. Commodity-interaction maps are essentially dictionaries of needs and the actions that satisfy those needs, and they are used to trade off compute time searching over all advertisements on all objects to see if they satisfy a sim’s needs with storage cost. The LoD optimizations tick the actions of sims not in the current focused level when they come into focus (auto-satisfy), and tick certain subsystems like the wants of the town itself at a lower rate (story progression). As a result, although the simulation notionally supports hundreds of characters, the vast majority of them are effectively idle at any given time. As well, although The Sims 3 has many more possible motives (needs) than the 8 used in previous versions, any individual character has a small number of those possible motives.

《The Sims 3》以创建一个更庞大、更多样的鲜活世界为目标，为了在做到这一点的同时保持可玩性，它采用了若干优化[36]。其中包括分层规划、需求资源与交互的映射等执行优化，以及自动满足曲线、故事进展等细节层次（LoD）优化[36]。通常的O(NLM)方法，会依次搜索每个人（N）、每个地点（L）、每个广告行动（M）；分层规划则改为每次只选择其中一个步骤，将复杂度变为O(N + L + M)。需求资源与交互的映射，本质上是需求及满足这些需求的行动所构成的字典；它们以存储成本，换取搜索所有物体的全部广告、判断是否满足某个模拟市民需求所需的计算时间。LoD优化会在当前关注层级之外的模拟市民进入关注范围时，更新其行动（自动满足），并以较低频率更新某些子系统，例如城镇本身的愿望（故事进展）。因此，虽然模拟在名义上支持数百个角色，但任一时刻，绝大多数角色实际上处于闲置状态。此外，虽然《The Sims 3》可能具有的动机（需求）远多于此前版本中的8种，但每个具体角色只具有这些可能动机中的少数几种。

3.1. Scoring functions 3.1. 评分函数

The scoring function that we use here is the most sophisticated function listed in Zubeks description of needs-based AI, an attenuated need-delta scoring function that is additionally attenuated based on distance [34]. One difference in our version is that each action can only satisfy one need. In the version of action performance outlined by Zubek, some actions can be sequences, and this can potentially allow for multiple needs to be fulfilled by an advertisement. As such, the algorithm for calculating an advertised action score must sum the attenuated scoring across all needs. Instead of summing across all needs, with each action only satisfying one need, we can simplify the attenuated need-delta scoring with distance attenuation to:

$$\mathit{score}=D(A_{need}(\nu_{current})-A_{need}(\nu_{current}+\delta))$$

我们这里使用的评分函数，是Zubek对基于需求的人工智能的介绍中列出的最复杂函数：它是一种经过衰减处理的需求增量评分函数，还会根据距离进一步衰减[34]。我们的版本有一处不同：每个行动只能满足一种需求。在Zubek概述的行动执行版本中，一些行动可以构成序列，因此一个广告可能满足多种需求。这样，计算某个广告行动分数的算法，就必须对所有需求的衰减后分数求和。而在每个行动只满足一种需求的情况下，我们不再对所有需求求和，可以把带有距离衰减的需求增量衰减评分简化为：

$$\mathit{score}=D(A_{need}(\nu_{current})-A_{need}(\nu_{current}+\delta))$$

where $\nu_{current}$ is the current need value of a particular need type, $\delta$ advertised need delta, $A_{need}$ is an attenuation function, and $D$ is the distance attenuation function. $A_{need}(x)=\frac{10}{x}$ as is discussed in Zubek, but instead of the mentioned $D(x)=\frac{x}{distance^2}$ function ours is $D(x)=\frac{x}{1+(\frac{distance^2}{2870})}$ to tune down the degree to which NPCs attenuate distance. The value 2870 was not chosen at random, it relates to the size of the map that the characters move on and effectively scales $distance^2$ to be between 1 and 30 (as opposed to a max of 82369).

其中，$\nu_{current}$是某种需求类型的当前需求值，$\delta$是广告所给出的需求增量，$A_{need}$是衰减函数，$D$是距离衰减函数。与Zubek所讨论的一样，$A_{need}(x)=\frac{10}{x}$；但我们没有使用其中提到的$D(x)=\frac{x}{distance^2}$函数，而是采用$D(x)=\frac{x}{1+(\frac{distance^2}{2870})}$，以减弱NPC对距离进行衰减的程度。2870这个值并非随机选择，它与角色移动的地图大小有关，实际上把$distance^2$缩放到1至30之间（而不是最大达到82369）。

One more simplification in the current demo is that all locations only advertise a single action. In effect, a location has a type that correlates to a need. As such, the complexity of this scoring algorithm can be given as O(NL), where N is the number of NPCs that need to select actions and L is the number of locations to search over.

当前演示还作了一项简化：所有地点都只发布一种行动广告。实际上，每个地点都有一个与某种需求相对应的类型。因此，这一评分算法的复杂度可以写作O(NL)，其中N是需要选择行动的NPC数量，L是需要搜索的地点数量。

4. Real-time logic programming 4. 实时逻辑编程

Each character has 6 motivations (hunger, bathroom, games, amusement, music, and shopping) that influence their action selection.

4.2. Implementation optimizations 4.2. 实现层面的优化

The performance of the system is dependent on several optimizations. Many of these have to do with the specific programming language implementation: strong typing, bottom-up execution, parallel execution, native code compilation. The details of the language implementation are outside the scope of this paper but see [37], [38] for more information.

系统性能取决于若干优化。其中许多与具体的编程语言实现有关：强类型、自底向上执行、并行执行、原生代码编译。语言实现的细节不在本文讨论范围之内，更多信息见[37], [38]。

Another important optimization might be called implicit need decay. Normally, a needs-based AI system would update each need state of each character on every tick. For our system, this would be prohibitively expensive. Instead, we store timestamped need values; a need value is represented as a tuple of $(v,t,\rho)$ stating that the need had value $\nu$ at time $t$, and was decaying at rate $\rho$. We can then compute the current need value on demand as:

$$\nu_{current}=\max(\nu-(t-t_{now})*\rho)$$

另一项重要优化，可以称为隐式需求衰减。通常，基于需求的人工智能系统会在每次更新时，更新每个角色的每一种需求状态。对于我们的系统，这样做的成本高到无法承受。因此，我们改为保存带有时间戳的需求值：需求值由一个元组$(v,t,\rho)$表示，意为该需求在时刻$t$具有值$\nu$，并以速率$\rho$衰减。这样便可以按需计算当前需求值：

$$\nu_{current}=\max(\nu-(t-t_{now})*\rho)$$

with $t_{now}$ being the current time. Since these values are read infrequently but would otherwise be updated frequently, this is much more efficient. As is recommended by Zubek, decay rates for a given need vary slightly from character to character to give them slightly different “personalities”. These decay rates are chosen randomly (Appendix A, Code Fragment 3).

其中，$t_{now}$是当前时间。由于这些值读取频率不高，而采用另一种做法却需要频繁更新它们，因此这样做高效得多。按照Zubek的建议，同一种需求的衰减速率，在不同角色之间略有差异，以赋予角色稍有不同的“个性”。这些衰减速率随机选取（附录A，代码片段3）。

4.3. Action States 4.3. 行动状态

For characters to perform a selected action they must move to the location of the selected action and then take some steps to complete the action before the need is satisfied. While we could allow for completion of actions instantaneously, to be more in line with The Sims implementation - as specified by Zubek – we instead have some action performance before a need is satisfied.

要执行已选行动，角色必须移动到该行动所在地点，再经过若干步骤来完成行动，之后需求才得到满足。我们原本可以让行动瞬间完成，但为了更贴近Zubek所描述的《The Sims》实现，我们选择先让角色执行一段行动，再满足需求。

When an action is initiated, the system tells the unity code to start moving the character, and then marks the character as being in progress towards that location. When the character arrives at the location they are marked as no longer moving towards their destination. When the action is completed, unity informs the system, and the system updates the need states, and generates a new next action (Appendix A, Code Fragment 6, 7, 8, 11). In place of the animations that would normally be running when performing an action, we simulate an animation running by starting a timer that indicates the selected action is being done (Appendix A, Code Fragment 9).

当一个行动开始时，系统告知Unity代码开始移动角色，再把角色标记为正在前往该地点。角色到达地点后，会被标记为不再向目的地移动。行动完成时，Unity通知系统，系统便更新需求状态，并生成下一个新的行动（附录A，代码片段6、7、8、11）。执行行动时通常会播放动画；我们改为启动一个计时器，以表明所选行动正在进行，借此模拟动画正在播放（附录A，代码片段9）。

Unlike in The Sims all actions in this simulation are individual, there is no chaining of actions nor are there any concurrent interactions. This simplification is what allows us to use a timer for each person taking an action, when the timer is running the “animation” is playing and when the timer completes the character has completed the action and finished its animation. While we do not have proper animations for each sim, when on a timer for an action the sim is moving randomly around the location that they have selected an action at.

与《The Sims》不同，本模拟中的所有行动都各自独立，没有动作链，也没有并发交互。正是这种简化，使我们能够为每个正在采取行动的人使用一个计时器：计时器运行时，“动画”正在播放；计时器结束时，角色便完成了行动，也结束了动画。虽然我们没有为每个模拟市民制作正式动画，但当行动计时器运行时，该模拟市民会在其所选行动的地点附近随机移动。

4.4. Destinations & Unity Interface 4.4. 目的地与Unity接口

For control of character movements, we have a simple interface between the action selection simulation and the Unity code that performs movements. The Simulog code provides a table of people and the destination they are moving to (Appendix A, Code Fragment 7) that the Unity code iterates over each tick to adjust NPC positions. The Unity code in turn provides a function that we can call to ask if someone has arrived at their destination. With this simple interface of action selection assigning destinations to the Unity code and Unity only needing to report back when someone has arrived at the destination, we are able to change out the underlying movement implementation without needing to do any modifications to the action selection algorithm. Currently, the movement is all simple vector addition moving sims at a set speed straight towards their destination.

为了控制角色移动，我们在动作选择模拟与执行移动的Unity代码之间，设置了一个简单接口。Simulog代码提供一个包含人物及其正前往的目的地的表（附录A，代码片段7），Unity代码在每次更新时遍历该表，以调整NPC的位置。Unity代码反过来提供一个可供调用的函数，用以询问某人是否已经到达目的地。通过这个简单接口，动作选择向Unity代码分配目的地，Unity则只需在某人到达目的地时报告回来；这样，我们便能够替换底层移动实现，而无须修改动作选择算法。目前，所有移动都是简单的向量加法，让模拟市民以固定速度，沿直线向目的地移动。

5.1. Pushing character counts 5.1. 提高角色数量

The performance shown above is only possible when we first compile our rules down to native C# code, the process for which is described in [37], [38], and then we run our compiled code in parallel. The type of parallelism employed is per predicate, not per sim, utilizing the dependency graph for all predicates to spin up tasks that run the compiled rules for a given predicate only when its dependencies have finished. Without these optimizations the maximum character count at nearly the same performance is 2000 NPCs.

要达到上述性能，必须先把规则编译成原生C#代码，再并行运行编译后的代码；编译过程见[37], [38]。所用并行方式是按谓词划分，而非按模拟市民划分：利用全部谓词的依赖图启动任务，只有当给定谓词的各项依赖都完成后，才运行该谓词编译后的规则。没有这些优化时，在近似相同的性能下，最多只能运行2000个NPC。

One optimization that could be employed to further stabilize performance (and potentially allow for more NPCs) is to throttle the number of characters that are selecting actions on a given tick. With a limit on the number of characters selecting actions that is slightly higher than the un-limited average number selecting you could effectively cap the cost of doing action selection while still eventually performing the same sets of needs-based calculations. This technique was not employed in this demo but a commercial system that cares more about never dropping below 60fps may want to implement such a throttle.

有一项可采用的优化，能够进一步稳定性能，并有可能支持更多NPC：限制每次更新中选择行动的角色数量。如果把选择行动的角色数上限设为略高于无限制时的平均选择人数，就可以有效限制动作选择的成本，同时最终仍完成相同的那组基于需求的计算。这个演示没有采用此项技术；不过，如果商业系统更看重绝不降至60fps以下，就可能希望实现这样的限流。

6. Conclusion 6. 结论

AI character control based on declarative programming can be surprisingly performant. Through a combination of compilation, parallel evaluation, and careful optimization, thousands of characters can be run at video frame rate. Although this demonstration involves simple needs-based AI, we intend to investigate more complicated techniques in the future.

以声明式编程为基础的人工智能角色控制，其性能可以高得令人意外。通过结合编译、并行求值和仔细优化，可以让数千个角色按视频帧率运行。尽管此次演示涉及的是简单的基于需求的人工智能，我们打算在未来考察更复杂的技术。
